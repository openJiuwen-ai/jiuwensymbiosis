# 架构检视：职责归属、依赖与所有权

本参考由 GitCode PR 检视和独立架构检视共用，规定分析方法和证据要求，不要求
生成 HTML，也不是第二份架构规范。项目约束来自目标版本的文档和实际接口；
分级、代码检视和合入建议由发起流程汇总。

## 1. 冻结证据，先建立原有模型

- 固定 base、head、比较范围及文档版本。PR 通常以冻结目标分支与 head 的
  merge-base 为起点；重新取远端数据不自动改变正在分析的目标。
- 分别读取 base 与 head 的约束、公开导出和关键调用方。用户明确提供的最新
  决策单独记录来源，不把工作区新文档混写成 base 已有事实。
- PR 自己的设计说明是待评估的意图。它可以提出架构演进，但不能仅凭“新增
  领域”证明目录归属正确，或只靠同步修改 AGENTS 就证明新模型合理。
- 先说明原来由谁负责契约、配置、设备实现、状态、资源和失败恢复，再描述
  新模型；不要从 head 的目录名称倒推系统本来应该这样组织。

JiuwenSymbiosis 的基线按适用范围从版本化的 `AGENTS.md`、
`docs/zh/explanation/architecture.md`、`docs/zh/tutorial/02-build-first-adapter.md`、
`docs/zh/how-to/port-hardware-adapter.md`、相关 `design/` 文档及已有同类实现取得。
按标题和符号定位，不依赖旧章节编号、固定文件数量或 skill 内缓存的项目概括。

文档与代码不一致时，分别记录声明约束与实际行为。机器人契约只在其适用领域
判断，不要求其他设备伪造 pose、joints 或 home；归入 adapter 也不等于必须继承
机器人专属基类。

## 2. 所有变更先筛查，按实际边界变化展开

查看移动／新增的生产模块、公共导出、配置分派和新增依赖。命中以下任一项时，
必须展开相应分析，不能等用户再次明确要求架构检视：

| 触发项 | 需要追查的实际关系 |
| --- | --- |
| 新增、拆分、合并或迁移生产模块 | 原有职责所有者、同类实现、新模块的真实消费者 |
| 新增 Registry、Session、Service 或执行入口 | 是否建立第二套契约、配置、任务、状态或生命周期权威 |
| 新增 adapter、接入模式、组合选择或配置 selector | 类型与实例是否混淆，差异属于设备实现还是通用组装 |
| 通用层加入设备／协议／场景分支 | 为何不能收在已有 adapter 或正确的依赖层内 |
| 依赖方向、公开契约、持久状态或资源所有者变化 | 新旧调用路径、写入权、获取／释放和失败恢复责任 |

局部算法、文案或测试没有这些影响时，写出筛查范围和不展开的理由即可。行数
不能替代判断；既有且不被本次改变的债务不扩成全仓审计。触发分析不等于存在
finding，也不强制绘图或新建报告文件。

## 3. 对每个新增或迁移的职责核对归属

不能只读新目录 README 或类名；至少追到实际校验的数据、创建的对象、使用的
协议和真实调用方。对每个触发项回答以下问题，保留源码证据：

1. **实际做什么？** 说明隐藏的复杂性，而非复述“领域层”“通用层”。检查
   Schema、配置、结果和失败条件是否已绑定特定设备、协议或场景。
2. **原来属于谁？** 查 base 的约束及至少一个适用的相邻实现；没有同类实现
   时写明无，不假装已有项目惯例。
3. **谁在使用？** 列当前消费者和变化维度。同一设备的多个函数调用不自动
   证明跨 adapter 通用；没有直接 I/O 也不证明属于通用层。
4. **为什么原有归属不够？** 比较增强已有模块、在 adapter 内共享与新增跨设备
   契约。语义需独立封装，不自动推出需要顶层包或第二套框架。
5. **接口隐藏了什么？** 区分有稳定语义的适配与纯转发；检查是否让上层掌握
   接入细节，或把一个职责拆到多个平行命名空间。
6. **下一个同类需求会改哪里？** 用与本次真实变化维度相邻的情形推演，如
   再接一种协议、同类型第二个设备或另一种设备组合。检查是否被迫新增固定
   组合目录、复制状态或修改通用层；不要求本 PR 提前实现未来能力。

不把“所有硬件相关代码都不能在顶层”写成机械禁令。通用契约、跨设备算法和
真正共享的工作流可以有顶层归属；合并或保留独立接入也应由契约和所有权差异
决定，不能预设历史 PR 的最终答案。

## 4. 追依赖、状态和资源，不止看 import

围绕受影响的真实入口，检查必要的成功及失败／关闭路径：

- 谁解析配置、选择实现并冻结；selector 代表接入类型还是设备组合。
- 谁定义动作；发现、权限、能力门控和执行是否读取同一契约。
- 谁观测、解释和更新状态；不同设备的同名状态是否被错误合并。
- 谁创建、释放连接、线程、子进程、任务和 lease；部分失败、取消、超时和
  重启后，谁保留未决工作、决定重试和确认清理。
- 共享层是否仍依赖具体 mapping、SDK、设备标识或内部对象。
- 替换旧职责时，原消费者、导入路径、配置和失败语义是否同步退出。

import 是线索，不是完整结论。同一接入拆成“顶层领域＋adapter”后相互调用，
可能首先是归属拆散；先比较收拢方案，再判断是否真需要抽象。无环依赖也不能
证明多个资源所有者或平行状态库合理。

## 5. 比较实质方案，区分发现与待决策

只比较会改变归属、依赖、状态或扩展成本的现实方案。优先检查已有 owner，不为
凑数量设计替代架构，不替作者补造将来复用的理由。

- 新职责明确、旧职责退出、依赖和迁移一致：可以是受控演进。
- 限制的范围、原因、代价和收敛触发明确：可以是已说明的架构债务。
- 违反已确认约束，或使职责、权威来源和恢复持续分散：形成有证据的发现。
- 多个合理归属仍取决于产品范围或 owner 选择：列待决策，解释可观察差异；
  不当成已证实的运行时 bug，也不静默选择自己喜欢的目录结构。

每个 finding 必须建立完整因果链：

```text
base 职责／约束及证据 → head 实际变化及消费者
→ 新依赖、所有权或扩展影响 → 失败代价或维护后果 → 所需修改或设计决定
```

使用发起流程的分级：正确性、安全、数据或并发风险按实际后果判 blocking；
可证明的职责漂移、重复机制或扩展成本按影响判 important；仅命名、排版或
可选整理判 nit。不能凭目录名报 important，也不能用测试通过消除架构发现。
文档遗漏与实现归属分别报告，补 AGENTS 不代表实现归属已经修复。

## 6. 检查文档是否随实现同步

从本次职责、公开契约或行为变化反查文档入口，不只查看 PR 是否修改了 Markdown，
也不以日期、提交时间或文档行数证明同步。即使文档未出现在 diff 中，也要读取
冻结 head 的实际说明，与相应实现逐项核对。

| 实现变化 | 按影响查找的文档与使用入口 |
| --- | --- |
| 模块归属、目录、依赖或资源所有者变化 | AGENTS、架构说明、设计文档、Source Tree、依赖图和相关协作指针 |
| 公共接口、导入路径、动作或能力变化 | API／动作参考、接入指南、公开导出示例和已有 Skill 文档 |
| 配置字段、默认值、模式或支持范围变化 | 配置参考、YAML 模板、示例配置、README 和既有中英文对应页面 |
| CLI、安装依赖、入口或协议版本变化 | 命令帮助、安装／部署说明、可复制命令及版本支持声明 |
| 生命周期、失败、重试、取消、持久化或迁移变化 | 运维、恢复、兼容／迁移说明及完成／停止语义的声明 |
| 工作流程、skill 或共享参考变化 | 调用该流程的 skill、CLAUDE／AGENTS 中的入口指针、默认交付格式及引用链接 |

沿变更的符号、字段、selector、路径和命令搜索活跃引用；历史记录与当前使用
说明分开处理。只展开本次受影响的文档，不要求每个内部实现调整都修改文档，
也不扩成全仓文档清理。

受影响时给出同步映射：

| 实现变化及 head 证据 | 应同步的文档入口及证据 | 状态 | 不一致造成的影响／所需修改 |
| --- | --- | --- | --- |

状态使用“已同步”“遗漏”“与实现矛盾”“待核实”；没有用户可见或架构变化时，
简述“无需文档变更”及理由即可。新能力没有既有说明时，指出应该承载它的现有
文档入口或待明确的归属，不能把找不到文档当成无需检查。

文档 finding 同时引用文档位置和对应实现，解释具体读者将怎样被误导。按实际
后果分级：可能导致危险操作、数据损失或绕过必要恢复的错误说明，可以形成
blocking，但必须证明因果；公开配置／接口失效、重大架构归属或支持范围误导
通常是 important；不改变使用与理解的排版、日期或措辞是 nit。不能把所有文档
问题降为 nit，也不能仅因没改 AGENTS 就自动阻塞。

区分“实现违反现有契约”和“有意改动但文档滞后”；不能通过改文档掩盖实现错误。
文档宣称的测试、SDK、设备或完成语义必须有对应证据，文本已更新不等于能力
已验证。同一根因在文档与架构／代码意见中交叉引用，避免重复计数。

## 7. 最小必交分析与术语

命中结构触发项时，意见至少包含职责变化表。相同职责可以合并成一行，但不能
省略未判为问题的触发项及其理由：

| 边界变化 | base 归属与证据 | head 实际职责与消费者 | 依赖／所有权／扩展影响 | 判断与所需决定 |
| --- | --- | --- | --- | --- |

再列分级发现、待决策项和证据缺口。每项发现引用 base/head 文件、符号和行号；
新增模块没有 base 对应文件时，引用原有所有者或约束文档。区分事实、推断、
owner 决策和未验证内容。未触发时简述筛查结论即可。另报告文档同步状态；
有影响时附第 6 节的映射，无影响时给出无需更新的理由。

术语沿用目标文档和公开接口；内部类名不自动成为架构概念。同词在不同子系统
语义不同时加限定，不另造上位词。例如区分 Execution Trace 回放与标定离线
重解；标定 Station 是采样组；REVIEW/candidate 不是可加载的正式标定文件；
本地写文件也不自动等于部署。只展开本次实际涉及的词。

本参考不代表已执行代码检视、测试或实机验证。是否回帖、如何汇总和给合入建议
遵循发起流程及用户授权；架构与代码两类判断均不能由测试结果代替。
