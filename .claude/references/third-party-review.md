# 三方件、依赖声明与许可证检视

用于 PR 检视中的三方件检查。以同一组冻结 base/head 为范围，从实际使用反查
声明和许可；不能因为 `pyproject.toml` 或 Notice 没有变化就判定没有引入三方件。
本参考规定检查方法，不预先批准某个组件或许可证，也不扩成全仓历史依赖清理。

## 1. 识别本次引入或改变的三方件

- 检查新增 import、动态加载、安装／下载命令、构建／部署配置、复制的代码、
  脚本、二进制及资源。覆盖新增、升级／降级、来源切换和使用／分发方式变化；
  仅改版本范围也要检查本次允许的已发布版本是否存在许可变化。
- 记录组件发行名称、版本或 commit、上游来源、用途和实际调用位置，区分直接
  依赖、受本次变更影响的传递依赖及随 wheel、容器或仓库分发的内置组件。
  区分声明范围、实际核验版本和已安装版本，不用本机偶然安装的包代表全部范围；
  未固定版本时说明核验边界，不宣称已覆盖未来版本。
- 未发现相关变化时，说明筛查范围与“未引入或改变三方件及许可”的依据，
  不要求无关 PR 修改清单。

## 2. 核对 pyproject.toml 声明

- 逐项检查 [`pyproject.toml`](../../pyproject.toml)：运行时依赖放在
  `project.dependencies`，可选能力放在对应 `project.optional-dependencies`，
  开发和构建依赖按项目现有分组及 `build-system.requires` 声明。
- 核对发行名称与 import 名称的映射、版本范围、extras 和环境 marker 是否覆盖
  实际调用条件。直接使用的 Python 三方包不能只依赖其他包的传递安装，
  也不能仅靠本机已安装、文档中的手动安装或未声明的运行时下载使测试通过。
- 已有声明确实覆盖本次使用时，引用现有条目，不机械要求新增一条。
  非 Python 系统库、外部 SDK、复制的源码或资源不伪造成 pip 依赖；注明
  `pyproject.toml` 不适用的原因及实际安装／构建声明位置，仍核对其许可证和 Notice。

## 3. 核对 Notice 与上游许可依据

- 对照 [`Open_Source_Software_Notice.txt`](../../Open_Source_Software_Notice.txt)，
  确认每项引入已有适用条目或随 PR 补齐：组件名称、核验版本／来源、真实版权
  声明、许可证名称及版本、相应许可全文和上游要求保留的 NOTICE／归属信息。
  沿用文件已有的同许可证全文复用格式，但须确认所指文本适用且完整。
- 证据优先取实际引入版本的源码标签、发行包／wheel 内的 LICENSE、COPYING、
  NOTICE 等文件，并给出永久链接或可定位的包内路径。包元数据和扫描结果用于
  交叉检查，不能用上游最新分支、许可证简称或占位版权替代实际版本的许可文本。
- 升级时检查旧条目是否仍适用；条目存在不等于版本、版权或许可已同步。复制
  代码保留原有许可证及版权头，修改标记和随包声明按上游条款核对；只补本项目
  的 Notice 不能替代上游要求。存在再分发时检查声明是否随实际制品交付，
  不只检查仓库中的文件。资源、模型权重等许可单独核对，不以 SDK 许可代替。

## 4. 判断与本项目的许可证兼容性

- 读取冻结 head 的 [`LICENSE`](../../LICENSE) 和 `pyproject.toml` 许可声明，
  核对两者一致；本项目当前为 Apache-2.0，后续检视仍以目标版本为准。
- 按“将该三方件引入本项目并按当前方式发布”的方向判断，结合源码复制、
  链接、插件、外部进程／服务和实际再分发边界，列出版权、许可／NOTICE 保留、
  修改标记、源码提供、再分发和用途等适用义务及是否满足。不能把“开源”
  “装在 extra 中”或“单独进程调用”直接当成兼容结论，也不能靠补 Notice
  消除不兼容。双许可证的 `OR` 选择、`AND` 组合和例外条款要明确记录依据。
- 兼容性标为“已核对兼容”“兼容条件尚未满足”“已确认不兼容”或“待核实”，
  附实际版本的许可文本证据、适用条款及集成方式。无法确认授权、版本或法律解释时，
  列出具体缺口和需维护者／合规负责人确认的事项，不自行宣称兼容或批准换许可证。
- PR 检视只读依赖声明、上游许可文本、分发配置及已有证据，不为核对许可
  安装／运行三方件或构建制品。依赖漏洞及自动合规扫描交由流水线，本地不执行
  扫描门禁；引用已有结果时注明对应版本／SHA。扫描通过与许可证兼容是不同结论。

核对条款时参考官方原文：[Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0)
及其[兼容方向说明](https://www.apache.org/licenses/GPL-compatibility.html)；
依赖声明参照 [PyPA 规范](https://packaging.python.org/en/latest/specifications/pyproject-toml/)。
这些参考不代替具体三方件版本的许可文本及本项目的实际集成判断。

## 5. 交付与合入判断

有相关变化时，在 PR 评论中逐项列出：

| 三方件、版本与来源 | 用途／使用和分发证据 | pyproject 声明或不适用理由 | Notice／版权及许可文本 | 许可证证据、兼容性与义务 | 问题等级／所需修改 |
| --- | --- | --- | --- | --- | --- |

- 缺少必要的依赖声明或 Notice／许可信息，通常列为 important 并要求补齐；
  同一根因与代码或文档发现交叉引用，不重复计数。
- 已确认的许可证冲突、缺少必要授权或无法满足强制许可义务，列为 blocking，
  建议先改再合；普通的 owner 风险接受不能替代授权或许可义务。
- 许可来源、兼容性或义务是否满足仍缺少关键证据时，建议“暂不建议合入：
  证据不足”，而不是将待核实写成兼容或可选 nit；未受影响的部分继续检视。
