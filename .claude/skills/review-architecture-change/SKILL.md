# 生成人工架构检视报告

将代码差异解释成一次系统模型的演化。报告的重点不是逐文件复述实现，而是回答：

- 原系统如何工作，各模块为什么存在，职责边界在哪里；
- 改动试图解决什么问题，引入了什么新概念和设计选择；
- 新系统的结构、依赖、状态和数据流发生了什么变化；
- 变化是受控的架构演进，还是正在造成边界模糊和架构腐化。

## 遵守检视原则

1. 先读取 `AGENTS.md`、相关架构文档和适用的项目规则，再检查 diff、base/head 两侧实现、公共接口和调用关系。
2. 以 base revision 代表的系统状态为设计起点，不从改动后的实现倒推并改写原模型。
3. 先还原原系统模型，再描述新模型，最后比较二者；不要直接从 diff 跳到结论。
4. 先解释“为什么改变”和“由谁负责”，再解释“如何实现”。函数内部细节只作为架构判断的证据。
5. 将事实、推断和未知分开。修改意图没有提交信息、issue、文档或用户说明支持时，明确标记为推断。
6. 将局部正确性、代码风格、常规安全检查和测试执行交给项目已有 rules/skills。本 Skill 默认不运行测试、lint、类型检查或硬件验证。
7. 除生成报告外，不修改产品代码、测试、配置或文档；不要替检视者批准改动。
8. 报告中不要自己造词。先建立项目术语台账，再写报告；术语以项目文档为准，代码标识符和 CLI 参数用于消歧，不得把报告作者的概括包装成项目概念。

## 建立并执行项目术语台账

在还原系统模型时同步记录一份工作用术语台账，不必原样展示在报告中。每个会进入标题、图、表或结论的核心名词至少记录：

- 项目采用的中文名称及对应代码标识符；
- 定义或稳定用法的文档路径、章节或符号；
- 所属子系统、所有者和准确语义；
- 是否由本次改动新引入，以及是否与既有术语同名异义。

按以下顺序确定用词：

1. 用户明确指定的术语；
2. 目标 revision 中与该子系统直接相关的设计文档和操作文档；
3. `AGENTS.md` 与公共接口、类型、CLI 帮助中的稳定名称；
4. 实现内部名称，只能作为代码标识符引用，不能自动提升为架构概念。

最新文档与 base revision 用词不一致时，不要静默选边：分别说明“原系统称为……”和“本次改动/当前文档称为……”，并判断这是有意重命名、概念变化还是文档漂移。

找不到权威中文名称时，使用普通描述加精确标识符，例如“离线重新求解（`--replay`）”。明确这是报告中的解释性表述，不要首字母大写、加引号或反复简称，使其看起来像项目已有概念。

特别防止以下语义漂移：

- 不要把 CLI 的 `--replay` 一律写成“回放”。本项目“回放”通常指 Execution Trace / `jiuwensymbiosis-replay`；标定流程应写成文档采用的“离线重解”或“从 station archive 离线重新求解”。
- 首次出现 `waypoint archive`、`station archive` 等代码术语时，沿用文档原词并立即解释用途，例如“自描述 waypoint archive（示教轨迹文件）”和“station archive（标定采样数据集）”；不要另造“事实档案”“轨迹资产”等上位概念。
- `Station` 在手眼标定中表示一组标定采样，不要译成物理“工位”或“工作站”。
- `candidate` 应写成 `REVIEW/candidate` 报告或 `*.candidate.json`，不要简称为可能被理解成可部署制品的“候选产物”。
- 不要写“写正式 schema”。schema 是格式约束；动作应写成“写出符合 schema-v2 的运行时标定 JSON”或项目文档已有的“发布正式标定”。
- “发布”必须说明实际副作用。如果实现只是写本地 `--out` 路径，就写“写入正式标定输出路径”，不要暗示上传、部署、注册或改变生产环境。

同一术语在不同子系统已有稳定含义时，优先使用更具体的限定词，而不是复用短词。图、表、标题和正文必须使用同一组名称；允许在首次出现时给出中英文或代码别名，之后固定使用一个名称。

## 确定设计起点

准确解析用户指定的 commit、range、branch、PR/MR、staged、worktree 或文件范围，并记录：

- 检视目标及 base/head revision；
- 当前 `HEAD` 和工作树状态；
- 改动规模、涉及的顶层模块和公共边界；
- 报告依据的是平台最新数据还是本地 Git ref。

分支和 PR/MR 默认使用 merge-base 作为设计起点。暂存区与工作区分开处理；同时存在多个合理范围时，不要静默合并。用户未明确目标且无法唯一判断时，先请求确认。

检视过程中只使用必要的 Git、搜索和源码读取操作。识别大规模重命名、移动、拆分和合并，因为这些变化常常表达职责迁移，而不只是文件变化。

## 还原原系统模型

在分析新实现前，基于 base revision 建立原系统模型。

### 设计目的与上下文

说明系统或目标子系统要解决的问题、服务对象和约束。记录该模型对应的 revision，避免把本次改动引入的中间问题误写成系统原始目标。

### 概念空间

识别原系统用于描述问题的核心概念。对每个概念说明：

- 它代表什么业务或技术含义；
- 它封装了什么复杂性；
- 它与其他概念如何关联；
- 哪个模块拥有它的定义和生命周期。

不要把类名和函数名的集合当作概念模型。概念应能解释系统为什么这样分层和协作。

### 职责与边界

说明相关模块、层和组件分别负责什么、不负责什么，以及：

- 依赖方向和允许的调用方向；
- 数据、状态、策略和生命周期由谁拥有；
- 对外接口与内部协作边界；
- 扩展点和应保持稳定的架构约束。

### 原有结构与流程

绘制或描述原有组件关系、主数据流、控制流和关键状态变化。流程必须使用前面建立的概念，而不是仅使用文件名串联调用。

## 描述新系统模型

### 改动目标与核心设计问题

从证据中概括改动要达成的目标。只展开两到三个真正控制设计的核心问题或取舍，例如职责应落在哪一层、能力应由哪个抽象提供、状态应由谁拥有。

### 新概念与设计选择

说明新增、改变、合并或废弃的概念。新概念必须有清晰语义和所有者，并能让设计逻辑比直接组合旧概念更简单。

对每项关键选择说明：

- 选择了什么；
- 为什么该职责属于这个模块；
- 与依赖模块已有能力如何分工；
- 采用完全封装、薄封装还是直接暴露；
- 被放弃方案的实质差异和取舍。

不要把临时实现机制提升为系统概念，也不要为了替代码辩护而事后创造概念。

### 新职责、结构与流程

描述修改后的：

- 模块职责和边界；
- 依赖关系及调用方向；
- 核心数据、状态和生命周期所有权；
- 对外接口和重要内部协议；
- 主数据流、控制流、失败与恢复流；
- 后续扩展方式。

复杂改动至少提供“组件与依赖”和“关键流程”两个视图。小范围改动只保留能帮助判断边界变化的视图。

## 比较前后模型

使用一张前后对照矩阵，至少覆盖适用的维度：

| 维度 | 原系统 | 新系统 | 变化原因 | 架构影响 |
|---|---|---|---|---|
| 概念及其所有者 | | | | |
| 模块职责与边界 | | | | |
| 依赖方向 | | | | |
| 核心状态与数据所有权 | | | | |
| 接口与封装策略 | | | | |
| 数据流、控制流与恢复流 | | | | |
| 扩展方式 | | | | |

按照职责变化组织叙述，不按照文件顺序组织。文件、符号和短代码片段只用于证明模型，不作为报告主体。

## 检查架构腐化

把“边界发生变化”和“架构腐化”区分开：

- **受控演进**：新职责明确，旧职责同步退出，概念、接口和依赖关系保持一致；
- **架构债务**：为了现实约束接受的局部妥协，有明确范围、原因和收敛方式；
- **架构腐化**：没有形成新的稳定模型，却让职责、依赖或真相来源持续变得模糊。

从以下维度检查：

### 职责与层次

- 本层是否承担了应由上层、下层或既有依赖模块负责的能力；
- 同一职责是否分散到多个模块，形成多个真相来源；
- 为了局部方便是否绕过了公共抽象、策略入口或生命周期所有者；
- 通用层是否开始包含特定 adapter、硬件或场景分支。

### 依赖与封装

- 依赖方向是否逆转、形成环或穿透多个层次；
- 封装是否泄漏下层知识，调用方是否必须理解内部实现才能正确使用；
- 薄封装是否只转发接口却没有稳定语义；
- 新能力是否重复实现已有模块能力，而不是增强正确的依赖层。

### 概念与接口

- 同一概念是否出现多个名称，或同一名称承载多个语义；
- 新接口是否对应真实概念，还是由布尔开关、可选参数和模式分支拼成多个隐含职责；
- 接口集合是否完整表达设计流程，内部协议是否与概念模型一致；
- 兼容层是否形成长期双轨模型，却没有清晰退出路径。

### 数据、状态与流程

- 数据或状态的所有者是否唯一，写入权和生命周期是否清楚；
- 同一转换、校验或策略是否在多个路径重复；
- 新流程是否引入隐藏的调用顺序、时序耦合或跨层回调；
- 失败与恢复是否仍由原有责任主体处理，还是散落到业务路径。

### 演进能力

- 新增同类能力是否仍能通过既有扩展点完成；
- 每增加一个 adapter 或场景是否都需要修改核心层；
- 文档中的系统模型是否仍与代码一致；
- 本次变化是否缩小了概念和边界，还是增加了必须共同理解的特殊情况。

不要只报告抽象的“代码味道”。每项架构发现都必须建立完整因果链：

```text
原有职责或约束 → 本次边界变化 → 新的依赖/所有权/流程 → 长期后果
```

## 应用 JiuwenSymbiosis 架构基线

架构基线以仓库最新文档为权威来源，不要信任本节内嵌的任何概括。每次检视时先读取以下文档建立基线，再以 base revision 的实现对照：

- `docs/zh/explanation/architecture.md` —— 架构总览、各层职责与数据流。重点对照：
  - 二、Env 层：唯一的硬件契约（`BaseRobotEnv` 为唯一 contract）
  - 三、API 层：动作契约与 `@implements`（`ActionSpec` 词表 + `api/defaults`）
  - 四、能力门控（Capability Gating）
  - 七、安全 Rails：横切策略与职责边界
  - 九、RobotSession：生命周期聚合器（env 与 sidecar 的唯一所有者）
- `docs/zh/tutorial/02-build-first-adapter.md` 与 `docs/zh/how-to/port-hardware-adapter.md` —— 新硬件通过配置与 adapter 扩展的完整流程；adapter 只承担配置、驱动和形体/几何差异的边界依据。
- `AGENTS.md` 的 “Architecture: Layered Capability-Gated Design” 与 “Hardware Adapter Pattern (6 files)” 节 —— 精简约束清单，用于快速定位，细节以上述 `docs/` 为准。

将内嵌的下列检查项仅作为提示，逐条回到上述文档确认其当前措辞与适用范围是否仍然成立：

- 动作契约（`ActionSpec` 词表 + `@implements`）组合机器人能力，硬件差异应收敛在 adapter，而不是扩散到核心层；
- Api、Tool、Rail 和 Agent 不应各自建立旁路硬件模型（`BaseRobotEnv` 为唯一 contract）；
- 工具暴露由 Api 与 Env capability 共同约束，新增能力不应破坏 capability gating；
- 通用实现负责可复用流程，adapter 只承担配置、驱动和形体/几何差异，反向重复也属边界异常；
- `RobotSession` 拥有 env 与 sidecar 生命周期，跨模块资源不应出现第二所有者；
- Rail 承担安全、恢复、反馈等横切策略，业务路径不应复制或绕过这些策略；
- 新硬件原则上通过配置和 adapter 扩展，修改多个核心层需解释既有扩展模型为何不足。

这些约束不是不可改变的教条。若改动有意调整它们，要求报告给出新的概念模型、职责分配、迁移范围和长期扩展逻辑；缺少这些内容时，将其列为设计决策缺口。若基线文档已演进，以文档为准并在报告中注明所依据的文档版本或 revision。

## 组织 HTML 报告

除非用户指定其他位置，将报告写入：

```text
<repo-root>/tmp/review-reports/review-architecture-change-<scope>-<short-sha-or-timestamp>.html
```

报告按以下顺序组织：

1. **页头与架构结论**：范围、base/head、设计起点、改动规模、结论和置信度；
2. **改动目标**：为什么改变、证据来源和仍未知的信息；
3. **原系统模型**：概念、职责边界、组件关系和原有数据/控制流；
4. **新系统模型**：新概念、设计选择、职责、结构、接口和新流程；
5. **前后对照**：展示边界、依赖、所有权、流程和扩展方式的变化；
6. **架构一致性与腐化发现**：按影响排序展示受控演进、架构债务和架构腐化；
7. **关键取舍与替代方案**：只讨论会改变职责分配或架构模型的实质方案；
8. **证据、未知与待决策项**：提供文件/符号证据，并保留人工最终判断。

架构结论只使用：

- 架构边界保持一致；
- 架构演进基本一致，存在局部债务；
- 存在需要明确的设计决策；
- 存在阻断性的架构腐化。

每项发现包含：类型、影响等级、原职责、发生的变化、证据、长期后果和建议决策。没有发现时直接说明，不为填充报告制造问题。

## 呈现与证据

- 使用 UTF-8 自包含 HTML5，内嵌 CSS，不加载远程脚本、字体、样式或图片。
- 使用安静、清晰的工程设计风格；优先展示系统模型、边界表、依赖图、数据流和前后对照。
- 复杂关系使用 HTML/CSS 或无脚本内联 SVG；代码和原始 diff 放在次要、可折叠的证据区。
- 对所有仓库内容和用户文本执行 HTML 转义。
- 仅在能可靠识别托管平台规则时生成固定到 commit SHA 的永久链接；否则显示路径、符号、revision 和行号。
- 提供响应式导航、键盘焦点和打印样式，确保桌面、移动端和 PDF 可读。
- 紧邻架构结论声明“最终合入决定由检视者作出”。

## 校验报告

完成前确认：

1. 原系统模型出现在新系统模型之前；
2. 每个新概念、职责变化和架构发现都有证据；
3. 前后模型使用一致术语，没有同义异名或异义同名；
4. 标题、图表和结论中的核心名词均能追溯到术语台账；无法追溯的词已改为普通描述，并附精确标识符；
5. 已检查跨子系统同名词，尤其没有混淆 Execution Trace 回放与标定离线重解，也没有把内部类型名误译成新的业务概念；
6. schema、candidate、发布等词准确描述了格式、可加载性和实际副作用，没有把本地文件写入夸大成部署流程；
7. 设计逻辑中的操作能映射到接口，状态和流程没有遗漏所有者；
8. 每项腐化判断都说明被破坏的原边界及其长期后果；
9. 报告没有退化成文件清单、diff 摘要、局部 bug 列表或测试结果汇总；
10. HTML 文件存在、非空、无外部加载资源，并返回绝对路径可点击链接。
