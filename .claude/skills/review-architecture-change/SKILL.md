# 架构变更检视

解释改动如何改变系统模型，并判断职责、契约和依赖是否仍然清楚。
按职责变化组织证据，避免逐文件复述 diff。

## 范围与基线

读取 `AGENTS.md`、适用规则及相关架构文档，解析用户指定范围。
记录 base/head、当前 HEAD、涉及的工作区内容和数据来源；
未查询远端时不要称为平台最新状态。

- 分支、PR/MR 默认用与目标分支的 merge-base 作为起点。
- 暂存区比较 HEAD 与 index；未暂存改动比较 index 与工作树。
  检视整体工作区时显式包含 staged、unstaged 和相关未跟踪文件。
- 根据用户上下文确定范围；只有存在会改变结论的多种解释时才请求澄清。
- 用只读 Git 操作读取两个版本，识别移动与重命名，不切换或覆盖用户工作树。

分别建立三个有版本依据的视角：

| 视角 | 证据 | 用途 |
|---|---|---|
| 修改前的实际模型 | base 的实现、接口、测试和当时文档 | 还原原职责与行为 |
| 修改后的实际模型 | head 或指定工作区的同类证据 | 确认真实变化 |
| 本次应遵守的约束 | 适用指令及明确采用的设计决策/文档版本 | 判断变化是否合理 |

当前文档不能自动成为历史事实。文档与代码不一致时，记录差异；
不要静默选边，也不要把新方案的目标倒推为原系统一直具备的能力。

## 还原并对照系统模型

先还原原系统，再建立新模型。对受影响范围说明：

- 要解决的问题、服务对象、约束，以及改动目标的证据；
- 核心概念、契约、数据与状态的所有者；
- 模块职责、依赖方向、公共接口与重要内部协议；
- 主数据流、控制流、失败恢复及资源生命周期；
- 新增同类能力时的扩展位置与修改成本。

变更意图没有提交、需求或设计文档支持时标记为推断。
只展开影响职责分配或行为的实质取舍，不为现有代码补造设计理由。

复杂改动可提供依赖图和关键流程图；局部变化使用简短对照即可。
前后对照至少说明适用的职责、接口、所有权和依赖变化及其原因，
不强制为未变化维度填表。

## 术语与项目约束

为报告中的核心术语记录工作台账：名称、代码标识符、定义来源、
所属模块及是否本次新引入。优先沿用用户指定和目标版本中的稳定名称；
无法确认的中文术语用普通描述加标识符，不创造新的上位概念。

检查同名异义、同义异名和文档漂移。首次说明别名后，在正文、图表和
结论中保持一致。涉及标定时才读取
[标定术语说明](references/calibration-terms.md)。

架构基线查阅 `AGENTS.md` 与 `docs/zh/explanation/architecture.md` 的相关部分。
涉及硬件扩展时再读取 `docs/zh/how-to/port-hardware-adapter.md` 和
`docs/zh/tutorial/02-build-first-adapter.md`。按受影响范围核对：

- 动作契约是否仍只有一个来源，工具暴露是否仍受能力门控；
- 硬件差异是否留在已有扩展位置，共享算法是否出现形体分支或反向依赖；
- 状态、感知新鲜度、资源及恢复策略是否保持明确所有者；
- 安全策略是否覆盖变化后的真实执行路径，而非仅存在于某个类中；
- 标定、GUI 等子系统是否遵守各自的依赖和延迟加载约束。

这些提示不另定义一套架构。若改动有意改变约束，检查新的职责模型、
迁移范围、旧路径退出条件及验证依据是否完整。

## 判断架构影响

- **受控演进**：新职责明确，旧职责同步退出，概念、接口和依赖一致。
- **架构债务**：局部妥协有明确原因、范围和收敛条件。
- **架构腐化**：职责或事实来源持续分裂，却没有形成新的稳定模型。

重点查找跨层侵入、重复契约/转换/策略、状态多处写入、隐含顺序耦合、
绕过生命周期、长期双轨兼容，以及每加一种硬件就修改核心的情况。
不要仅凭类多、文件小或一行转发判为腐化：动作绑定和有稳定语义的转发
可以是合理接口；关键是调用方是否因此获得清楚且可验证的契约。

每项发现必须建立因果链：

```text
原职责或约束 → 本次变化 → 新依赖/所有权/流程 → 可说明的长期后果
```

使用 [改动验证映射](../../references/change-validation.md) 找到相关检查，
标明已有覆盖、仍需补充的检查与人工判断。现有测试只能证明其断言覆盖的范围；
没有执行时明确写“仅检查测试源码”。

默认进行静态检视，不运行测试或硬件操作；用户要求验证时运行范围内合适的检查。
审查本身只产出报告；产品修复须属于用户另行或同时授权的任务。

## 交付

默认在回复中给出 Markdown；用户要求报告文件时写入指定位置，
未指定则使用 `tmp/review-reports/` 下包含范围与 revision 的唯一文件名。
仅当用户要求 HTML 时读取 [HTML 报告规范](references/html-report.md)。

先给出结论及置信度，再依次呈现适用内容：范围与目标、原模型、新模型、
关键变化、按影响排序的发现、验证证据与未知项。
每项发现包含类型、影响、证据位置、长期后果和建议决策。

区分边界一致、受控演进、局部债务、待明确决策和阻断问题；
证据不足时明确无法判断。没有发现就直接说明，不为填充报告制造问题。
引用路径、符号、revision 和行号；只有确认托管规则时才生成 commit 永久链接。
最终合入决定由检视者作出。
