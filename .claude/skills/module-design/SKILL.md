# 模块设计

从问题、已有模型和约束推导职责与接口，使实现者知道设计为什么成立、
哪些条件必须保持，以及如何验证。

## 范围与交付

- 先读取 `AGENTS.md`、涉及模块的公共导出、调用方、附近测试及相关设计文档。
  不依据文件名或目录层级臆测职责。
- 用户指定设计范围、格式、文档位置时遵循其要求。已有设计就在原文档上修订；
  新的完整设计按仓库惯例写入 `design/` 下语义明确的 Markdown 文件。
- 局部决策可以直接用简短说明表达，不强制创建文件或填满模板。
  涉及公共契约、职责归属、状态机或生命周期的复杂改动才展开相应视图。
- 设计任务本身不授权实施产品改动。若用户已要求设计并实现，完成设计后继续实施，
  不额外插入审批步骤。必要的验证使用无硬件测试或离线探针。

## 建立设计起点

说明要解决的实际问题、服务对象、成功条件和范围；目标应解释为什么改变。
记录设计基于的 revision，涉及工作区改动时说明其范围。

先还原相关的现有模型：概念、所有者、接口、状态与资源生命周期、
依赖方向和失败处理。区分代码事实、文档约束、推断与未知；
文档与实现不一致时写明差异。

修改已有设计时保留原问题和设计起点。若需求或基线确实变化，显式记录变化，
不要将实施中的临时问题改写为最初目标。

## 分配职责与比较方案

围绕真正影响结果的取舍展开，不为凑数量制造替代方案：

- 对每项能力，检查已有模块是否拥有它；优先增强正确的所有者，避免在调用层复制。
- 新模块要说明封装了什么复杂性、服务哪些调用方，以及为何需要新的协作接口。
  一行转发若承载动作绑定或稳定语义可以合理存在，不单凭行数判断抽象价值。
- 确定完全封装、有限暴露还是直接使用已有接口，并说明调用方需要掌握的知识。
- 对新增概念先查既有术语；确有不同语义时再命名，说明所有者与已有概念的关系。
  数据结构、接口和图中的名称保持一致。
- 比较会改变职责、依赖、扩展成本或失败语义的实质方案。
  不为假想的未来硬件预建多套框架。

项目约束从 `AGENTS.md` 和 `docs/zh/explanation/architecture.md` 获取，
只展开受影响部分。特别关注动作契约的唯一来源、能力门控、
硬件差异的归属，以及状态和资源是否出现第二所有者。

## 表达数据、接口和流程

描述足以约束实现的核心数据结构、所有权及关系。已有接口在重构中保持不变时，
指出沿用的定义及兼容条件，不必复制整份接口手册。

对每个受影响的接口，按适用性说明：

- 输入、结果形状、单位、坐标系和有效范围由谁定义与校验；
- 前置条件、状态变化、位置新鲜度，以及未知状态的处理；
- 失败如何呈现、失败后的状态、重试或恢复责任，是否允许部分完成；
- 资源的获取、释放、幂等性、并发、取消及必要的调用顺序。

这些条件会影响接口能否正确使用，不能一律推迟为“实现细节”。
新增动作时复用 `ActionSpec` 的规划契约，不另建一份状态或顺序模型。
涉及内部协议或线程协作时，补充决定行为的内部接口。

用 Mermaid 展示有助于推理的依赖、状态或时序关系；简单关系用文字或表格即可。
从目标出发串起正常流程和关键失败流程，检查每一步都有明确的执行者。

## 约束、迁移与验证

使用 [改动验证映射](../../references/change-validation.md) 定位已有检查，
为受影响的关键约束记录：

| 约束 | 责任模块 | 现有检查及需补充的验证 |
|---|---|---|

可自动判断的契约、依赖方向和失败语义优先扩展已有测试。
难以自动判断的职责取舍明确保留人工判断，不把设计文档视为验证结果。

若调整既有架构，说明旧职责如何退出、调用方如何迁移、兼容期如何结束，
以及哪些文档和检查需要同步更新。无需迁移的局部设计不展开该部分。

## 完成检查

确认目标、概念、职责、数据结构和接口一致；关键状态及非法输入有处理策略；
失败与资源清理没有遗漏所有者；安全、可测试性和诊断需要已反映在接口中。

文档可按“目标与基线 → 方案与取舍 → 数据/接口/流程 → 迁移与验证”组织，
只保留适用部分。正文呈现最终方案；对理解约束仍有价值的被否决方案保留理由。
迭代时更新相关章节和实质决策记录，不把探索过程逐条堆进正文。

回复给出设计文件链接或简短方案、主要决策，以及实际验证和待解决的问题。
