# GitCode PR 检视与回帖

流程为获取 PR → 冻结版本 → 静态检视 → 修正轮 → 回帖。架构和代码两项都检视，
两类意见都回帖；测试及自动门禁交由流水线，不在本地重复执行。
发现默认按第 5 节的 blocking / important / nit 分级；发起流程另有明确分级时，
说明对应关系后沿用，不依赖仓库外的 skill。
架构分析必须使用共享的[架构检视方法](../../references/architecture-review.md)；
用户另需独立架构报告时，使用
[review-architecture-change](../review-architecture-change/SKILL.md) 选择交付格式。

## 1. 冻结审查目标

- PR ref 是 GitLab 风格：`git fetch upstream refs/merge-requests/<N>/head`。
  GitHub 风格 `pull/<N>/head` 在 GitCode 上**不存在**。remote 约定：
  `origin` = 个人 fork，`upstream` = canonical 仓；PR 挂在 upstream。
- 记下 head SHA 作为审查目标标识。**`FETCH_HEAD` 会被任何后续 fetch 覆盖**：
  本轮任何 `git fetch`（包括顺手 fetch main）之后，一律用显式 SHA 引用目标。
- `git merge-base <sha> upstream/main` 求基线。若 PR 含不属于本 PR 的提交
  （分支叠在其他未合入 PR 上），先 `git fetch upstream main` 看 main 是否已
  推进吸收它们 —— main 可能在审查期间合入其他 PR；**有效差异 = 相对最新
  main 的差异**，不要把已被 main 吸收的提交算进审查范围。
- PR 可能相对对照文档被 rebase / force-update：文档记录的 SHA 与当前 head
  不一致时，按当前 head 重新冻结目标，并在检视意见中指出（例如文档里的
  "基于 commit X" 基线陈述已过期）。
- 取数结束后记录目标分支 SHA、merge-base 和 head，本轮两类检视都使用这组
  冻结值。审查中 main 或 head 改变时，不静默切换目标；若需采用新差异，
  重新冻结并复核两类结论。

## 2. 静态检视边界

- 使用 `git diff`、`git show <sha>:<path>` 等读取冻结版本的源码、测试和文档；
  需要目录搜索时可用 `git archive` 导出独立快照，不混入当前工作树的其他改动。
  不为检视预先创建测试环境、安装依赖或配置 editable import wrapper。
- 本轮不运行测试、复现脚本、lint／格式检查、类型检查、构建、漏洞／合规扫描
  或其他自动门禁，也不导入执行被检视代码、启动服务或连接硬件。测试及自动
  门禁由流水线负责；读取测试源码、配置和已有结果仍属于静态检视。
- 引用已有流水线结果时注明任务、链接及对应 SHA；旧 SHA 的结果不能代表本轮
  head。不可见时写“未读取”，未结束时写“待流水线完成”，不等待、轮询、
  触发重跑或为定位失败展开本地执行。用户另行要求诊断时再按其范围处理。

## 3. 架构检视（必做）

- 必须读取[共享架构分析方法](../../references/architecture-review.md)，对所有
  PR 先做结构筛查；命中其中的模块归属、平行机制、接入／组合、依赖或所有权
  变化时，展开对应分析，不能等待用户再次要求架构检视。
- 按共享参考核对 base 的已有所有者、head 的实际职责与消费者、既有归属为何
  不足，以及下一个同类需求的变化位置。必须追实现和相邻调用方，不能仅靠
  新模块的名称、README 或自称的“领域独立”判断归属。
- 结构触发项必须进入共享参考规定的职责变化表，每项有判断理由；不能只
  报“AGENTS 未更新”而漏掉实现归属。没有结构影响时简短说明筛查范围即可。
- 同时按共享参考的文档同步方法，从职责和实现变化反查 AGENTS、架构说明、
  配置／API／CLI 文档、模板及示例；检查未被 PR 修改的相关说明。文档改过
  不代表已同步，文档没改也不代表必然有错，必须核对具体声明和实现。
- 默认以 Markdown 表格和证据链输出，不因需要架构检视就生成 HTML/SVG。
  用户明确要求相应可视化报告时，再使用独立架构 skill 的呈现分支。
- 先形成架构判断，再进入第 4 节检查具体实现。架构存在问题或信息不足时，
  仍须完成可执行范围内的代码检视；两项各自记录结论、发现和证据限制，
  不能以架构未通过为由跳过代码检视。

架构结论与后续工作：

| 架构结论 | 判定 | 下一步 |
| --- | --- | --- |
| 通过 | 本 PR 范围内无未解决的实质架构问题，关键事实与设计归属已明确 | 继续代码静态检视；此时尚不能给出整体“可合” |
| 存在问题 | 存在 blocking／important 架构发现，或影响归属、依赖、所有权的关键设计仍待决定 | 保留分级架构意见，继续代码静态检视，最终统一给出合入建议 |
| 信息不足 | 缺少判断架构所必需的基线、实现或设计依据 | 列明缺失证据，继续独立检查可读取的实现；代码若同样缺少依据，也须明确其覆盖限制 |

纯文案、格式等可选 nit 不构成实质架构问题；确实改变职责或所有权的问题不能
为了给出可合建议而降为 nit。owner 明确调整原有架构约束时，记录该决策后
重新核对架构判断，不能替 owner 接受设计风险。

## 4. 代码静态检视（必做）

- 对与第 3 节相同的冻结 base/head 检查实现正确性、权限与安全、生命周期、
  错误处理、兼容性、三方依赖与许可证，以及测试源码是否覆盖关键分支。
  架构结论不决定本节是否执行，流水线通过也不抵消静态发现。

- 范围：`git diff --name-status <merge-base>..<head>`，按提交归属分组；
  对照物 = `AGENTS.md`（架构权威）+ 用户提供的意图/方案文档。
- 沿 diff 追真实调用方、公共契约、共享路径及错误／清理分支，不能只看新增
  目录或变更行。对照 base 区分既有问题与本次引入的问题。
- [改动验证映射](../../references/change-validation.md)仅用于定位应阅读的测试
  源码和覆盖职责，不执行其中的命令。检查断言、夹具及遗漏分支，避免把测试
  文件存在当成行为已验证；需要动态确认的事项明确标注并交由流水线覆盖。
- 仅凭已有的偶发失败记录不能断言竞态或环境污染。源码推断与流水线观察分开
  表述，不把未执行的复现写成已证实，不自动复跑或扩大测试范围。
- **发布前逐条核对引用行号**，从冻结 head 的文件内容确认路径和行号。
- 对外文本一律**仓库相对路径**（`jiuwensymbiosis/xxx.py:123`），不用本地
  快照路径；不引用只有本地能看到的文档路径，表述自包含。

### 文档同步核对（架构与代码两类检视共同覆盖）

- 根据本轮实际确认的接口、配置默认值、行为、依赖和失败语义，补全共享参考
  规定的文档同步映射；检查命令、导入路径、可复制示例和现有双语对应说明。
- 结论标明已同步、遗漏、矛盾或待核实；没有受影响说明时给出无需更新的理由。
  文档遗漏不能只停留在本地笔记，须进入 PR 意见并引用文档与实现证据。
- 文档问题按实际使用风险分级，与架构／代码发现共同影响合入建议；同一根因
  交叉引用而不重复计数。用户可见配置、恢复或能力声明错误不能一律当作 nit。

### 三方件、依赖声明与许可证核对（必做筛查）

- 每个 PR 都从实际 import、安装／下载、复制代码及资源等变化判断是否引入
  或改变三方件，不能只看依赖文件是否修改。命中时读取
  [三方件检视方法](../../references/third-party-review.md)并逐项核对。
- 检查 Python 依赖是否在冻结 head 的 `pyproject.toml` 正确声明，
  `Open_Source_Software_Notice.txt` 是否包含适用的组件、版本、版权及许可文本，
  并以本项目 `LICENSE` 和三方件实际版本、集成／分发方式判断兼容性及许可义务。
- 有相关变化时，PR 评论须包含三方件核对表和兼容性结论；未引入或改变时
  简述筛查依据。
  声明遗漏、许可冲突及待核实事项按共享参考进入分级与合入建议，不能因测试
  通过、Notice 已修改或 owner 接受风险就跳过必要授权及强制许可义务。

## 5. 分级与合入建议

默认分级如下；级别由具体影响和证据决定，不按文件类型或改动行数决定：

| 等级 | 含义 |
| --- | --- |
| blocking | 已证实会导致安全边界失效、数据丢失、关键路径不可用，或存在明确许可冲突／缺少必要授权等严重问题，必须修复 |
| important | 实质性的正确性、兼容性、凭据保护、职责归属或维护问题，需要修复或由 owner 明确接受具体剩余风险 |
| nit | 不影响正确性、契约或安全的局部表达、格式等可选改进 |

合并架构与代码两类发现，按最高未解决等级给出建议，同时考虑实际已检查范围和
静态证据是否充分。两类检视均为必做；未完成或受限的部分如实说明，不能表述
为“没有问题”。合入建议基于静态检视，实际合入仍受平台流水线门禁约束；
不在本地执行测试或门禁本身不构成检视未完成，也不因此一律判“证据不足”。

| 情况 | 合入建议 |
| --- | --- |
| 任一 blocking 未解决 | **建议先改再合**；不能以测试通过或其他阶段通过抵消 |
| 三方件许可来源、兼容性或强制义务是否满足缺少关键证据 | **暂不建议合入：证据不足**；列明缺口及待确认事项，不能按兼容处理 |
| 关键架构决策未收敛 | **建议先改再合**；列明待决定事项，同时提交已完成的代码检视意见 |
| 任一类检视有未解决且未被 owner 明确接受的 important | **建议先改再合**；说明影响和需要修改的内容 |
| 两类静态检视均已完成、无 blocking、关键设计决策已明确、静态证据充分，important 的具体剩余风险已被 owner 明确接受 | **有条件可合（基于静态检视）**；列出接受者、风险范围和明确条件，不替 owner 接受 |
| 两类静态检视均已完成、静态证据充分，仅有可选 nit 或无发现 | **可合（基于静态检视）**；nit 列为可选改进，不代表流水线门禁已通过 |
| 判断所需的关键源码、契约或设计依据缺失 | **暂不建议合入：证据不足**；列明静态证据缺口，不能用“有条件可合”掩盖未知 |

已知的流水线失败单独注明，不默认归因于本 PR，也不以静态“可合”解释为可以
绕过门禁。流水线未完成或结果未读取时可以完成静态检视和回帖，保留其状态。

交付至少包含：审查目标 base/head、架构检视结论及分级意见、代码检视结论及
分级意见、文档同步状态与受影响入口、三方件声明／Notice／许可证兼容性结论、
静态检视范围与限制、已知流水线状态及对应 SHA、基于静态检视的合入建议。
注明“本轮未运行本地测试或门禁，测试与门禁由流水线负责”；没有读取结果时
直接说明，不把静态阅读写成测试或运行时验收通过。
没有发现的类别也明确写出检查范围和“未发现问题”；证据不足时写明缺口。
两类意见都须按第 7 节提交到目标
PR，不能只在本地或对话中交付其中一类。

## 6. 修正轮

- 请求方批注修正发现后：在冻结版本中**复核其证据行号**再收编；过度宽泛的
  表述按批注收窄（例：某类拒绝实际走意图持久化前的干净路径，不在问题范围）。
- 修正稿改完再走一遍行号核对；引用已有复现数据时注明来源及对应 SHA，
  不编造本轮执行结果。
- PR 修复导致 head 或有效审查差异改变时，重新冻结 base/head，复核架构
  与代码两类意见及静态证据，使两份结论都对应当前候选；已有流水线结果标明
  对应 SHA。不能静默移动基线后混用旧结论，也不能因某类仍存在问题而省略
  另一类的复核和回帖，不为修正轮自动执行测试或门禁。

## 7. 回帖到 GitCode PR

- 执行目标 PR 的完整检视时，架构与代码两类意见都必须回帖。默认在同一条
  Markdown 评论中分别列出“架构检视意见”“代码检视意见”“文档同步”
  “三方件与许可证”“流水线状态与合入建议”；
  用户要求分开发表时，两条评论都标明同一组 base/head。
- 用户已经要求将检视意见回帖时，不重复询问是否发布；若用户明确限定只读、
  不回帖或仅编辑本 skill，则遵守该范围，不由此启动真实 PR 检视或发布。
- 缺少凭据、API 失败或回帖受阻时，保留包含两类意见的完整评论草稿，报告
  具体阻塞，不得把“本地完成”声称为“已回帖”。
- API 是 Gitee 风格 v5，匿名可读、写需令牌：
  - `GET https://gitcode.com/api/v5/repos/{owner}/{repo}/pulls/{n}` —— PR 元数据
  - `GET|POST .../pulls/{n}/comments` —— 评论列表 / 发评论
- **默认到发布时才获取凭据**：先完成两类检视、文档同步及三方件检查和完整评论草稿，
  再检查发布进程是否已有非空的 `GITCODE_TOKEN`，或用户指定的
  `GITCODE_TOKEN_FILE`（文件内容为个人访问令牌，路径可由用户提供）。没有时
  才询问用户配置环境变量或提供本地令牌文件路径，不要求把令牌贴进对话。
  仅当 PR 读取本身需要认证时，提前获取读取所需的凭据并说明原因；只读或
  仅修改本 skill 的任务不为回帖索取凭据。
- **SSH 私钥不能代替 API 令牌**；文件须由用户管理并仅当前用户可读，不扫描
  家目录或猜测密钥路径。使用发布评论所需的最小权限；遇到 401/403 时核对
  令牌有效性及仓库／评论权限，不自动申请或扩大权限。
- 只在发送请求的进程内读取令牌并构造认证头；不把值写入临时文件、源码、
  评论、命令行参数、URL、日志或工具输出。不要用 `cat` 显示令牌文件，
  不使用 shell 展开认证头或开启请求调试。允许去掉文件末尾换行，拒绝空值
  及内部空白／控制字符；认证头不能跟随重定向发送到其他地址。
- 发布后不复制、删除或修改用户提供的令牌文件，也不默认要求吊销已有令牌；
  临时令牌的撤销按用户约定处理。保留评论 Markdown 草稿供修正轮引用。
- 正文是 Markdown，JSON 编码和认证均在进程内完成。下例仅在用户已授权回帖、
  目标仓库／PR 已核对且凭据已就绪时执行；替换目标和草稿路径，不填入令牌值：

  ```bash
  python3 - <<'PY'
  import json
  import os
  from pathlib import Path
  from urllib.error import HTTPError, URLError
  from urllib.request import HTTPRedirectHandler, Request, build_opener

  class NoRedirect(HTTPRedirectHandler):
      def redirect_request(self, req, fp, code, msg, headers, newurl):
          return None

  token = os.environ.get("GITCODE_TOKEN", "")
  if not token:
      token_file = os.environ.get("GITCODE_TOKEN_FILE")
      if not token_file:
          raise SystemExit("缺少发布凭据；请配置环境变量或提供本地令牌文件路径。")
      try:
          token_path = Path(token_file).expanduser()
          if token_path.stat().st_mode & 0o077:
              raise SystemExit("令牌文件须仅当前用户可读。")
          token = token_path.read_text(encoding="utf-8")
      except (OSError, UnicodeError):
          raise SystemExit("无法读取令牌文件。") from None
  token = token.rstrip("\r\n")
  if not token or any(ord(c) <= 32 or ord(c) >= 127 for c in token):
      raise SystemExit("令牌为空或格式无效。")

  url = "https://gitcode.com/api/v5/repos/<owner>/<repo>/pulls/<n>/comments"
  body = Path("/tmp/pr<N>-review-comment.md").read_text(encoding="utf-8")
  request = Request(
      url,
      data=json.dumps({"body": body}).encode("utf-8"),
      headers={"Authorization": "Bearer " + token, "Content-Type": "application/json"},
      method="POST",
  )
  try:
      with build_opener(NoRedirect()).open(request, timeout=30) as response:
          status = response.status
  except HTTPError as error:
      raise SystemExit(f"回帖返回 HTTP {error.code}；先检查评论列表再决定是否重试。") from None
  except (URLError, OSError):
      raise SystemExit("回帖网络异常，结果待核实；先回读评论，避免重复发布。") from None
  if status != 201:
      raise SystemExit(f"收到 HTTP {status}，尚未确认发布成功；请回读评论。")
  print("HTTP 201；仍须回读并核对评论。")
  PY
  ```

- 验证：使用相同的凭据读取方式执行 `GET .../comments`；HTTP **201** 后回读
  已发布评论，核对 author、
  body、base/head，以及架构、代码意见、文档同步和三方件与许可证结论均已出现；

  超时或连接中断不能证明未发布；先回读核对，未确认前不自动重复 POST。

## 回顾清单

| 环节 | 易错点 |
| --- | --- |
| 取 PR | `refs/merge-requests/N/head`；FETCH_HEAD 会被后续 fetch 覆盖，用显式 SHA |
| 定范围 | 取最新目标分支后冻结 base/head；变更目标必须重新冻结并复核 |
| 两类检视 | 架构按共享方法主动筛查和判断归属；无论是否有问题都继续代码检视 |
| 文档同步 | 从实现变化反查活跃文档、命令和示例；按实际影响分级，不能只看文档 diff |
| 三方件与许可证 | 从实际使用反查 pyproject、Notice 与上游许可；核对本项目兼容性及义务，结论进入 PR 意见和合入建议 |
| 测试与门禁 | 本轮只读源码、测试及已有结果；由流水线执行，不本地复跑、不轮询等待 |
| 合入建议 | 合并两类静态发现，按最高未解决等级和静态证据给出；实际合入仍受平台门禁约束 |
| 引用 | 行号发布前逐条核对；仓库相对路径；表述自包含 |
| 回帖 | 两类意见都提交到目标 PR；发布时按需获取凭据，令牌仅进程内读取；201 后回读核对，结果不明先查再重试 |
